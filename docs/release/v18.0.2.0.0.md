# Release record v18.0.2.0.0

Release 18.0.2.0.0 adds the features that people expect of a document application on top of the
folders, members, trash, legal hold, quota and audit log of release 18.0.1: one workspace screen,
favourites, locks, duplicate and rename, versions, shortcuts, requested files, roles and end dates
for shared access, a mailbox for a folder, automatic filing of attachments, PDF split and merge, and
a details panel. It upgrades 18.0.1.0.0 in place.

Out of scope, as before: anonymous links ("anyone with the link"), spreadsheets, e-signature and
automatic recognition of bills.

## 1. What users get

### Workspace screen

- The **Documents** menu opens one screen. On the left: the folder tree (with counters), the
  sections and the tags. In the middle: the files the user may see as cards or as rows, an activity
  view, and the existing document form on click. The screen shows exactly what the user's own search
  over documents returns; it adds no right.
- **Sections** (one choice): *My files* (I am the owner), *Shared with me* (I am in the document's
  direct share list), *Recent* (changed in the last 30 days), *Starred*.
- **Stars.** Anyone who can read a document can star it (no write right needed). A star is private:
  nobody reads another user's stars, a document administrator included.
- **Buttons** that need no selection: *Upload* (choose a folder where you may upload, add several
  files and optional tags; a refused file is reported by name and does not stop the others), *New
  link*, *New folder*, *Trash*.
- **Cards** show a small copy of an image file (lazy, privately cached) or a large icon for the kind
  of file (PDF, text, sheet, archive, link, shortcut, requested file), with the name, folder, tags,
  owner, activity mark and small marks for starred, locked and "has versions".
- **Folders above the files**: the sub-folders of the folder chosen on the left, with the number of
  files they hold, and a path line (breadcrumb) in which every part is a way back.
- **Selection** by click (Ctrl or Cmd to add, Shift for a range). The control panel then offers
  *Open*, *Download*, *Share* and an *Actions* menu: rename, move, duplicate, star, create shortcut,
  ask for a file, new version, split or merge PDF, lock or unlock, move to trash. Entries that do not
  apply to the selection are hidden; the server judges every call again.
- **Opening**: a double click (or Enter) opens a file in the standard file viewer; a link opens in a
  new tab (http, https or mailto only); a shortcut opens its target; a requested file opens its upload
  dialog.
- **Dropping files** from the computer onto the cards uploads them into the chosen folder (or the
  folder card they are dropped on), one request per file, with progress and the server's refusal for
  each file that fails. Selected cards can be dragged onto a folder to move them.

### Details panel

Select a file and switch the info button on: the panel shows the kind, name, size and last change;
the folder, owner, contact and company; the tags (editable for those who may change the document);
where the file came from, with an *Open* button (shown only when the user may read the source
record); the star and the lock; the number of versions; who the document is shared with (names,
roles, end dates) and a *Share* button for those who may manage shares; for a requested file, the
person asked, the due date and the upload button. Under it is the chatter of the record. The form of
a document has a *Details* button that shows the same panel on a page of its own.

### Lock, duplicate, rename

- **Lock / Unlock.** While another user holds the lock nobody else can change the name, file, link,
  folder, tags, description, type, owner, contact, properties or archived state of that document, or
  move, trash, restore or delete it. Stars, chatter, activities and sharing keep working. The holder,
  a manager of the folder and a document administrator can unlock (the owner of the document can not, unless he is the holder or has one of those rights). Operations on a whole
  folder are not stopped by locks inside it. A lock is released by the server when its holder loses
  the right to write the document.
- **Duplicate** copies files and links into the same folder, named "(copy)" (translated), owned by
  the caller, with the tags and description (not shares, lock, legal hold, chatter). At most 20
  documents per call; upload policy and quota apply.
- **Rename** is a small dialog for a document or a folder; it performs a normal write as the user.

### Versions

A file keeps its history. *New version* makes the new file current and keeps the previous content as
the newest version; the name keeps its stem and takes the new extension. Each version can be
downloaded, made current (the current content becomes a new version) or deleted. The latest 20
versions are kept. A document under legal hold keeps all its versions (a new version that would push
one out is refused). Every replacement of the content of a file by a user, also a direct write
through the API, keeps the previous content as a version; the superuser and server paths do not. ZIP
downloads hold the current content only; purging a document removes its versions and their files.
Version numbers are never reused.

### Shortcuts

A pointer to a file or link in another folder, without copying it. It takes the target's name when it
is made (never synchronised afterwards), belongs to the person who made it, has no size and does not
count against the quota. A shortcut never gives access: if the viewer may not read the target (no
access, trashed, gone) the row is greyed out and *Open target* answers with one neutral message. A
shortcut cannot point to a shortcut, a folder or a requested file, and cannot be duplicated or
versioned. Share users never see shortcuts.

### Requested files

*Ask for a file* (folder form, action menu): what is needed, the folder, the person asked (an internal
document user who can store a file there), days until due, tags, a note. The person asked gets an
"Upload Document" activity and uploads the file onto the placeholder, which becomes an ordinary file.
The requester can send a reminder (at most once every 20 hours; the mail has no access code and its
link needs a login) and anyone who may write the request can cancel it by trashing it. A request
grants no right. Share users never see placeholders.

### Roles and end dates

- Folder members and document shares can have an **Access ends** date (not in the past). The last day
  of access is that date; a scheduled action that runs every 30 minutes then removes the row.
- A single document can be shared with a person as **viewer or editor**. An editor by share can rename
  the document, replace its content, change tags and description and trash it; an editor by share
  cannot move it to another folder, change its owner, manage who it is shared with, or restore it.
  A portal contact with an active account can be a viewer only.
- The *Shared with* tab and the *Share* button of a document and of a folder show the list; the
  folder dialog has one choice for "all document users": no access, view, upload or edit.

### Folder mailbox

A document administrator gives a folder an e-mail address (Configuration, *Folder mailboxes*).
Colleagues who follow the mailbox record, and who at that moment are active internal document users
with upload level or more on the folder, e-mail files to it: each attachment (up to 10 per mail)
becomes a document owned by the sender with the mailbox tags. The text of the mail is not kept;
nothing of the mail stays on the mailbox, only a short note with counts.

### Automatic filing

A document administrator creates a *Filing rule* (Configuration) for a kind of record (for example
projects): files attached to such records are also filed as documents in a chosen folder, with chosen
tags and owner. The person attaching the file needs no document right. When the original attachment
is deleted the filed document goes to the trash (an option; a document under legal hold stays).
*File existing attachments* files what was attached before, in batches, and can be run again. The
form says plainly that everyone who can open the target folder sees the filed files.

### PDF tools

*Split PDF*: page ranges typed as `1-3, 4, 5-8` or one document per page; each part becomes a new
document in the same folder, with the tags of the original. *Merge PDF files*: two or more selected
PDF documents, in the order the user sets, into a new document in a chosen folder. The originals are
kept; a check box moves to the trash those the user may write. Limits: 500 pages per source, 100
documents per split, 50 files per merge (2,500 pages in all). Password protected, damaged or non-PDF
content gives a short message.

### Other

- The **attachment overview** ("Attachments in other apps", from 18.0.1.1.0) is on by default for
  document users, with the source of every row labelled.

## 2. Data model changes

New persistent models (all added to the list of models whose attachments are never public and never
carry an access token):

| Model | Purpose |
|---|---|
| `woow.document.favorite` | one row per document and user |
| `woow.document.version` | one row per earlier content of a file |
| `woow.document.share` | one row per person a document is shared with (role, end date) |
| `woow.document.mail.intake` | the mailbox of a folder (alias, tags) |
| `woow.document.auto.rule` | an automatic filing rule |

Transient models: upload (with lines), rename, version, shortcut, request, fulfil, autofile and PDF
split and merge wizards (with merge lines), and a shared abstract mixin that checks the references a
wizard row names.

New fields on `woow.document`: `document_type` gains `shortcut` and `request`; `lock_uid`,
`lock_date`, `is_locked`; `version_ids`, `version_count`, `version_last_number`; `shortcut_target_id`,
`shortcut_target_available`; `request_user_id`, `request_deadline`, `request_note`,
`request_activity_id`, `request_last_reminder`; `share_ids`, `shared_editor_user_ids`,
`woow_user_can_share`; `source_attachment_id`, `auto_rule_id`; `favorite_ids`, `is_favorite`,
`woow_section`, `woow_icon`. Fields set by the server are refused in an RPC `create` or `write`.
`woow.document.folder.access` gains `expiry_date`. `ir.attachment` gains one internal-only link to
the documents filed from it.

## 3. New public methods and routes

Methods that can be called over RPC (each starts with its own access check and is listed in the
repository's public-method register): `action_toggle_favorite`, `action_lock`, `action_unlock`,
`action_duplicate`, `action_open_rename_wizard` (document and folder), `action_new_version`,
`action_open_shortcut_wizard`, `action_open_shortcut_target`, `action_open_fulfil_wizard`,
`action_send_reminder`, `action_open_share_dialog` (document and folder), `action_open_pdf_split_wizard`,
`action_open_pdf_merge_wizard`, `woow_inspector_data`, `action_open_source`, `action_open_inspector`;
on versions `action_download`, `action_restore`, `action_delete`; the wizard buttons (`action_upload`,
`action_rename`, `action_confirm`, `action_create`, `action_fulfil`, `action_file`, `action_split`,
`action_merge`); `action_open_backfill` on filing rules. The mailbox model overrides `message_new`,
`message_update` and `message_post` of core's mail gateway.

One new route: `GET /woow_document/version/<id>/download` (login required). It answers a missing, a
hidden and a forbidden version with the same page as the download of a document.

## 4. Security notes

- **Folder access stays the single source of truth.** Every new feature is judged by the folder
  rules and the record rules; the screen and the panel only read through the ORM as the user.
- **Elevations.** Five places use a different environment, each registered and tagged for the
  repository's static check, and each as small as it can be:
  - *Folder mailbox (S4)*: the gateway runs as the superuser, which skips folder checks on create, so
    the document is created in the environment of the **sender** (`with_user`). This lowers rights: the
    upload level, company rules, tags, upload policy and quota are judged exactly as for an upload in
    the interface. The same function decides at alias time and at storing time.
  - *Automatic filing (A1)*: the person attaching a file is usually no member of the target folder, so
    the filed document is created as the superuser; the rule made by a document administrator is the
    authorisation. Upload policy and quota still apply, the whole filing runs in a savepoint and any
    failure is swallowed so an attachment is never broken, and an in-process marker prevents
    recursion. Only the administrator-made rule decides what is filed where.
  - *Automatic filing (A2)*: before filing, the record the file is attached to is read in the
    environment of the **maker of the rule** (`with_user`), so a rule never files what the record rules
    deny its maker. Read only; lowers rights.
  - *Lost locks (S5)*: when a share row or member row is removed (including by the expiry cron), the
    server finds the locks it affects (superuser, search only), asks in the **holder's own
    environment** whether the holder can still write the document, and clears the lock when not. The
    only write is clearing the lock, logged as a forced unlock.
  - *Version limit (S6)*: a person who may replace the content only through a share (an editor by
    share) has no right to delete history, but the replacement they are allowed to make removes the
    oldest version when the limit of 20 is reached. That one removal runs as the superuser, after the
    document has been checked: it is refused outright for a document under legal hold, and the removed
    version is logged.
- **Server-only fields and markers.** Fields that only the server may set are refused in RPC calls.
  Markers that switch behaviour (a filing, a share synchronisation, a version swap, a requested-file
  fulfilment, a shortcut creation) are in-process objects; a context value sent by a client is never
  honoured as one.
- **Editors by share** gain exactly one extra way to write (rule on document write, active document,
  folder not in the trash). They cannot move or re-own the document, manage shares, restore it, or
  read or change the history of versions beyond what any reader of the document can; the version row
  that keeps the content they replace is created by the server under a create-only rule.
- **Expiry** is enforced by a scheduled action that runs every 30 minutes (at most 500 member rows and
  500 share rows per run, asking to be run again while rows are left). Access ends at the next run, not
  at midnight. End dates are compared with the server date in UTC.
- **Share users** (portal and public) never see shortcuts or requested files (two global record
  rules), and have no access to the new models or fields.
- **Locks** refuse changes by other users on every path: write, trash, restore, move, new version,
  restore of a version, a requested-file upload, and the trash option of the PDF tools. A lock never
  hides or reveals anything; the message names neither the holder nor any hidden record.
- **PDF parsing limits.** Files are inspected before any page is read: raw markers are counted, the
  page tree is walked once per node with a node limit, a parse time budget applies, and inflated
  stream sizes are capped, so a small hostile file cannot cost an unbounded amount of time or memory.
  Page, output and input counts are limited as in section 1.
- **Wizard reference checks.** A wizard row can name only documents and folders that the caller's own
  search finds; a missing and a hidden id get the same answer, and context defaults cannot smuggle in
  an unchecked id.
- **Attachments.** Every file of the new models is stored through the module's upload policy and
  quota; attachments of the new models are never public and never carry a token.
- **Default attachment overview.** Document users can see the overview of attachments of other apps
  by default; it shows exactly what the user's own search over `ir.attachment` returns, and the
  module's own files stay out of it. It adds no access right and no privilege escalation.
- **Audit.** New event keys: lock, unlock, duplicate, version add / restore / delete, request create /
  done, access expire, auto file, mail in, PDF split and merge. Details hold ids and counts only; no
  names, addresses or file content.

## 5. Deployment notes

- **Folder mailbox.** It needs (1) an alias domain with an MX record to the mail server and a catchall
  address, (2) a way to hand mail to Odoo (an incoming mail server polled by fetchmail, preferably IMAP,
  or the mail gateway script), and (3) an inbound mail server that **enforces SPF, DKIM and DMARC**:
  the module trusts the sender address that the gateway delivers, and a forged From address of an
  allowed sender would pass the module's checks. Allowed senders are the followers of the mailbox, and
  the sender's address must be the address of the user's contact. Outgoing mail is needed only for
  bounces and for request reminders (which also need the public address setting used for notices).
- **Automatic filing, requests, PDF tools, versions, shortcuts, sharing, workspace, details panel:**
  nothing to configure. A filing rule files nothing until it exists and is not retroactive (use *File
  existing attachments*).
- Scheduled action added: *Documents: End expired access* (every 30 minutes).
- Limits are constants in the code (20 versions, 200 shares per document, 500 pages per PDF, and so
  on); upload limits, file types and the quota of the module apply to every new path.

## 6. Upgrade notes (from 18.0.1.0.0)

- Upgrade in place with `-u woow_document_management`. New tables and columns are created; existing
  data stays valid. Existing documents are unlocked, have no versions and no shortcut target.
- One migration creates a **viewer share row without an end date for every entry already in a
  document's direct share lists** (idempotent; the lists do not change). A document shared with more
  than 200 people migrates whole; only adding a person is refused until it is under the limit.
- **Check before upgrading: the attachment overview group.** Since 18.0.1.1.0 the *Document User* group
  implies the *Attachment Overview* group, so every document user is a member of it. If any folder lists
  that group as a member, that folder is open at that level to all document users. Look at the member
  lists of folders for that group before upgrading and remove it where it is not meant.
- The old documents action stays installed; only the menu entry points to the new screen. Without the
  browser code the standard views keep working.
- **Going back** after the upgrade means restoring the database taken before it; the new tables and
  columns are not removed by installing 18.0.1 again, and the new document types would not be understood
  by it. Take a database backup first.
